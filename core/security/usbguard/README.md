# Chakra USB Guard (Phase 8)

The real `usbguard` daemon (not a custom reimplementation), configured as the first thing to actually enforce a policy from `/etc/chakra/policy.d/` — Phase 5 wrote `usb-storage.policy.json` as a schema example with nothing to enforce it; this is that enforcer, as honestly as the current architecture allows.

## Default behavior

- **Devices already connected at boot** (keyboard, mouse, installer media, etc.) are allowed. Live-boot means every boot is effectively a fresh machine to usbguard — there's no persistent history to build trust from over time — so a `chakra-usbguard-bootstrap.service` oneshot unit runs `usbguard generate-policy` before the daemon starts, allowing exactly what's plugged in at that moment (the standard, documented usbguard bootstrapping method for an unknown-inventory system). `PresentDevicePolicy=allow` in the daemon config is a second safety net for the same thing, in case the bootstrap script fails for any reason — your own keyboard shouldn't be able to get locked out.
- **New devices plugged in after boot are blocked by default** (`InsertedDevicePolicy=block`).
- **A blocked insertion raises a desktop notification** — `usbguard-notifier` runs in the session (autostarted, `/etc/xdg/autostart/chakra-usbguard-notifier.desktop`) and pops "USB device blocked: `<name>`". The desktop user can listen for these because an `IPCAccessControl.d/:sudo` entry grants the `sudo` group `list,listen` on the usbguard IPC (see `IPCAccessControl.d/chakra-desktop` in this dir). The `usbguard-dbus.service` bridge is enabled for it.

## The gap, honestly

`usb-storage.policy.json` says unknown USB storage should be **asked about** in Daily mode. usbguard has no built-in interactive "ask" prompt, and the notifier above is informational only — it tells you a device was blocked, it doesn't give you an "Allow" button. So the flow today is *notified* block + a manual `sudo usbguard allow-device` (below), not a one-click prompt. That is materially better than the silent block it used to be, but a real interactive prompt — a notification with Allow / Block / Allow-permanently actions, wired to the IPC — is still Phase 9 work. The IPC ACL deliberately withholds `modify` from the session for now, so building that prompt is also a decision to let a user-session component authorise hardware.

## Allowing a device after boot

```bash
usbguard list-devices          # see what's blocked, note its ID
sudo usbguard allow-device <id>
```

To make an allow permanent across reboots, add a matching rule to `/etc/usbguard/rules.conf` directly — though remember this rootfs's rules.conf gets regenerated by the bootstrap service on every boot from what's *currently* connected, so a manually-added rule for a device that isn't connected at the next boot won't persist as-is.
